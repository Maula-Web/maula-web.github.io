# Reglas del Proyecto

- **Commit automático obligatorio y detallado**: Siempre que se realicen modificaciones, correcciones, nuevas funciones o ajustes en los archivos del repositorio, se debe hacer automáticamente un `git commit` descriptivo y detallado (siguiendo *Conventional Commits*: `feat:`, `fix:`, `style:`, `refactor:`, etc.), indicando claramente en el mensaje y cuerpo del commit de qué modificación se trata exactamente, qué componentes o elementos se han alterado y el motivo del cambio, seguido de `git push`.
- **Anuncios en el teletipo**: NO anunciar modificaciones técnicas o de diseño en el teletipo de forma automática. Para cada cambio, ajuste o mejora que hagamos en la web, preguntar siempre al usuario si desea anunciarlo en el teletipo; si el usuario no contesta a la pregunta o pasa a otro tema, se asume que NO se debe anunciar. Las noticias de resultados, marcadores, aciertos, clasificaciones, líderes, botes y métricas derivadas de datos en vivo de la web se muestran de forma 100% automática.
- **Soporte dual obligatorio (Modo Oscuro y Modo Claro)**: Cualquier nueva característica, componente o ajuste visual debe diseñarse, implementarse y verificarse simultáneamente para ambos modos (Modo Oscuro por defecto y Modo Claro bajo `.light-theme` / `css/light-theme.css`), garantizando legibilidad, contraste y armonía estética en ambos entornos.
- **Verificación crítica previa ante discrepancias**: Cuando el usuario indique que algo está mal o pida alterar una mecánica de cálculo o contabilidad, verificar primero de forma rigurosa y objetiva si lo que afirma es correcto contrastándolo con el reglamento de la Peña, los archivos de documentación (`CONTEXTO_TECNICO_MAULAS.md`, `MANUAL_BOTE.md`), el histórico y la lógica del sistema. Si el usuario está equivocado o su premisa es inexacta, NO cambiar el código: razonárselo y explicárselo primero con datos, pruebas y consecuencias antes de tocar nada.
- **Protocolo de "Revisa" vs. "Revisa y Corrige"**: Si el usuario dice únicamente "revisa", "analiza" o "mira esto" (sin pedir corrección explícita), NO cambiar ningún archivo de código; limitarse a analizar, diagnosticar a fondo, presentar lo encontrado con claridad y preguntar si desea implementarlo. Solo cuando el usuario indique explícitamente "revisa y corrígelo", "corrígelo", "hazlo" o dé una orden directa de implementación, proceder a modificar el código directamente.
- **Actualización obligatoria y automática del Documento Técnico (`CONTEXTO_TECNICO_MAULAS.md`)**: Cada vez que se repare, modifique, actualice o incorpore cualquier función, componente, ajuste o lógica en la web o en los scripts del proyecto, se debe actualizar obligatoria y automáticamente `CONTEXTO_TECNICO_MAULAS.md` documentando detalladamente la regla de negocio, los archivos y funciones implicadas, el diagnóstico y el comportamiento esperado, sin esperar a que el usuario lo solicite expresamente.
